# VoxQuery: Data Integration & Handoff Guide
**From:** Frontend & Voice Subsystem   
**To:** Data Engineering & Platform Integration   
**Subject:** Wiring the Core Engine to the Kaggle E-Commerce Dataset

---

## 1. Executive Summary: Where We Are Today

We have successfully completed the architectural build-out for the **Voice Subsystem** and the **"Executive Concierge" Frontend**. 

The system currently runs as a decoupled, production-ready engine:
- **Frontend:** A Next.js, Framer Motion-powered React application using an "Ambient Intelligence" design pattern (Ready → Thinking → Insight). 
- **Voice Pipeline:** Real-time WebSockets successfully stream audio to Deepgram (STT) and return synthesized responses (TTS).
- **LLM Engine:** Claude Haiku (claude-haiku-4-5-20251001) is actively generating SQL and Data Narratives based on system prompts.
- **Observability:** Langfuse telemetry and Upstash Redis session stores are fully wired and persisting production traces.

### The "Catch": 
To allow the frontend engineers to build the UI at high velocity without waiting for the data warehouse to be provisioned, the backend utilizes a standard software engineering practice: **Stubbing**.

Currently, the `SnowflakeWarehouseConnector` is configured to intercept the real SQL generated by Claude and return a hard-coded, 3-row dummy response (`North America, Europe, Asia`). This prevents the application from crashing while the real database credentials are missing. 

**The system is not hard-coded; it is simply waiting for to connect the real database.**

## 2. The Target State: The Kaggle Dataset

The objective for the Data Engineering team is to replace the stubbed connector with live data, specifically targeting the **1M Orders Synthetic U.S. E-commerce Dataset**.

**Dataset Reference:**  
[`https://www.kaggle.com/datasets/limjeongeun/synthetic-u-s-e-commerce-dataset-1m-orders`](https://www.kaggle.com/datasets/limjeongeun/synthetic-u-s-e-commerce-dataset-1m-orders)

When this integration is complete, an executive should be able to ask the VoxQuery orb: *"What were our total sales by product category last quarter?"* and receive an accurate chart and voice narrative generated directly from the Kaggle dataset in Snowflake.

## 3. The Integration Checklist (Next Steps)

To achieve the target state, we must execute the following bare-bones sequence. 

### Step A: Provision the Snowflake Data Warehouse
The VoxQuery backend expects to execute standard SQL against a live Snowflake environment.
1. **Host the Data:** Extract the Kaggle CSV and load it into a properly structured Snowflake database/schema (e.g., `voxquery_db.ecommerce.orders`).
2. **Create a Service Account:** Provision a dedicated, **Read-Only** Snowflake Service Account for VoxQuery. *Security Note: Because an LLM generates the SQL, this account must not have `DROP`, `DELETE`, or `UPDATE` privileges.*
3. **Connect the Backend:** Update the VoxQuery backend `.env` file by replacing the dummy fallback with the live credentials:
   ```env
   # Inside backend/.env
   WAREHOUSE_PROVIDER=snowflake
   SNOWFLAKE_DSN=snowflake://<user>:<password>@<account>/<database>/<schema>
   ```

### Step B: Vectorize the Schema for the AI (Schema-RAG)
Claude cannot generate correct SQL unless it knows exactly what tables and columns exist in your Snowflake database. We use a Retrieval-Augmented Generation (RAG) pattern via Supabase `pgvector`.
1. **Extract DDL:** Export the schema definitions from your newly created Snowflake Kaggle tables (e.g., `order_id (VARCHAR)`, `category (VARCHAR)`, `sales_amount (FLOAT)`).
2. **Embed the Context:** Write a Python script to chunk these schema definitions, pass them through OpenAI's `text-embedding-3-small` model, and insert the vectors into the `schema_chunks` table in the Supabase PostgreSQL database.
3. **Add Semantic Glossaries (Optional but Recommended):** If the Kaggle dataset uses specific jargon (e.g., "AOV" = Average Order Value), embed a semantic data dictionary into the vector store so Claude understands executive acronyms.

### Step C: End-to-End Prompt Tuning & UAT
Once Snowflake and the Schema-RAG are connected, the system is fully "live." 
1. **Vibe Check:** Open the VoxQuery UI and speak 10-15 test questions related to the Kaggle dataset.
2. **Monitor Langfuse:** Open the Langfuse Observability dashboard. Review the exact SQL Claude is generating.
3. **Iterate:** If Claude hallucinates a column name or generates an incompatible Snowflake SQL dialect (e.g., using a Postgres function instead of a Snowflake function), adjust the core system prompts inside `backend/app/llm/claude.py` until the SQL generation achieves a 95%+ success rate.

## 4. Architectural Boundaries (Do Not Touch)

As you integrate the data, **do not modify** the following boundaries, as they will break the frontend UI:
- **Result Payload Shape:** The `SnowflakeWarehouseConnector` must continue to return `ResultPayload` (rows/columns) and `ResultShape` (chart types). Do not change the JSON structure.
- **WebSocket Contracts:** Do not alter the async event emissions (e.g., `progress`, `result_ready`, `clarification_requested`) inside the pipeline execution block.
- **Row Limits:** The connector currently enforces a hard limit (`LIMIT 10000`) on all LLM-generated SQL to prevent UI memory blowouts on the 1M row Kaggle dataset. Retain this safety net.
